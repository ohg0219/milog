# milog

CloudWatch 에 JSON 한 줄로 쌓이는 로그를 **브라우저에서** 읽는다. **AI 에이전트(MCP)도** 같은 방식으로 읽게 할 수 있다.
Log4j2 `JsonTemplateLayout` + OpenTelemetry 규약을 알고 읽어서, 레벨·소요시간을 컬럼으로 세우고
요청(trace)마다 색을 달리하고 span 중첩을 들여쓰기로 보여준다.

```bash
npm i -g @ohg0219/milog
milog
#   milog  →  http://127.0.0.1:52413/?t=ae644d04-…
```

설치는 스코프 이름으로, **명령은 `milog`** 로 쓴다.

로컬 서버를 띄우고 브라우저를 연다. 프로필·로그 그룹 선택부터 실시간 추적까지 전부 화면에서 한다.

```
16:49:00.023 INFO  5b434bc396de ● GET /orders/detail                    58ms
16:49:00.022 INFO  5b434bc396de   ↳ OrderService.findDetail              2ms
16:49:00.022 INFO  5b434bc396de     ↳ SELECT orders                      1ms
16:49:00.021 INFO  5b434bc396de     · OrderService  재고 확인 완료
16:50:00.014 ERROR a41c9d0e77b3 ● GET /orders/pay                     1204ms  ERROR
      ✗ java.lang.IllegalStateException: 상품 정보를 찾을 수 없음
```

## 무엇이 좋은가

- **trace_id 를 클릭**하면 요청 하나가 span 트리로 열린다. waterfall 로 어디서 시간이 새는지 본다.
- **타임라인**에서 에러가 몰린 구간이 빨갛게 보이고, 끌어서 그 구간만 볼 수 있다.
- 긴 `db.statement`·스택 트레이스·객체 덤프를 **자르지 않고** 본다.
- 한글 로그가 안 깨진다 (AWS CLI 를 거치지 않고 SDK 로 직접 읽는다).
- **Claude Code 같은 AI 에이전트에 붙일 수 있다** (`milog mcp`). "최근 1시간 에러 요약해줘", "이 trace 왜 느렸어?" 에
  원본 줄 대신 **예외별로 묶은 요약과 span 트리**를 준다 — [AI 에이전트에서 쓰기](#ai-에이전트에서-쓰기-mcp).

## 요구 사항

- **Node 22.12 이상**
- `~/.aws/config` 에 프로필이 있고, 그 자격증명으로 CloudWatch Logs 를 읽을 수 있을 것

프로필이 없으면 만든다:

```bash
aws configure sso --profile my-logs
```

| 프롬프트 | 예시 |
|---|---|
| `SSO session name` | `my-sso` |
| `SSO start URL` | `https://<조직>.awsapps.com/start` |
| `SSO region` | `ap-northeast-2` |
| 계정·역할 | 로그가 있는 계정 / CloudWatch Logs 읽기 권한이 있는 역할 |
| `CLI default client Region` | 로그 그룹이 있는 리전 |

- `[profile ...]` 바로 위의 `#` 주석은 목록에서 설명으로 쓰인다.
- 토큰이 만료되면 `aws sso login` 을 알아서 띄운다.
- 프로필이 많으면 `--profile-prefix <접두어>` 로 목록을 좁힌다.

잘 안 되면 **`milog doctor`** 부터. Node·한글 출력·프로필·자격증명을 차례로 짚어 준다.

## 명령

```
milog                        브라우저에서 보기 (기본)
milog -p my-logs -g qa-web   프로필·그룹을 미리 고른 채로 시작
milog --port 8080 --no-open  포트 고정, 창은 직접 열기
milog doctor                 환경 진단
milog mcp -p my-logs -g qa-  AI 에이전트용 MCP 서버 (아래 참고)
```

| 옵션 | 뜻 |
|---|---|
| `-p, --profile` | AWS 프로필 (부분일치) |
| `-g, --group` | 로그 그룹 (부분일치·반복·콤마) |
| `--region` | 리전 (미지정 시 프로필의 region) |
| `--profile-prefix` | 프로필 목록을 접두어로 좁히기 |
| `--port` | 기본 `0` = 빈 포트 자동 |
| `--no-open` | 브라우저를 자동으로 열지 않음 |
| `--idle-minutes` | 접속이 없으면 종료 (기본 30, `0`=무제한) |

## 화면

```
[my-logs › qa-web +1 ▾] │ [실시간|에러|검색] [자동 스크롤 ●] [날짜 2026-08-13 ~ 08-14 ▾] [조회]    [설정]
[검색어 ...........................................]      ← 검색일 때만
```

왼쪽 **소스 pill** 을 누르면 프로필·로그 그룹을 고르는 팝오버가 열린다.
프로필을 바꾸면 그룹 선택은 비워진다. 조작부는 전부 왼쪽에 모여 있고, 화면 아래에는
타임라인 말고 아무것도 없다 — 상태는 전부 상단 한 곳에서 읽는다.

`자동 스크롤` 을 끄면 새 줄이 와도 보고 있던 위치가 안 밀린다.

### 모드는 셋이다

| 모드 | |
|---|---|
| **실시간** | 5분 전부터 계속 따라간다. 누르면 바로 시작 |
| **에러** | 날짜 구간 안에서 **ERROR·FATAL 과 예외**만 |
| **검색** | 날짜 구간 안에서 **검색어**로 찾는다. 비우면 그 구간 전체 |

각 모드는 보낼 조건을 **하나만** 갖는다. 안 보이는 칸의 값은 아예 안 보낸다 —
감춘 조건이 몰래 걸리면 왜 안 나오는지 알 길이 없다.

#### 검색과 에러를 왜 섞지 않나

CloudWatch 는 **텍스트 패턴과 JSON 패턴을 한 요청에 못 섞는다.** 둘을 합치면 검색어가
원본 줄 전체가 아니라 `message`·`logger`·`span.name` 세 필드만 훑는 좁은 검색으로 바뀐다.
같은 trace_id 로 실측하면 검색어만 줬을 때 37줄이 나오던 것이 **에러를 함께 켜면 0줄**이 된다
(그 요청에 ERROR 가 분명히 있는데도). 느려서가 아니라 **답이 틀려서** 나눴다.

### 날짜

날짜 pill 에 빠른선택(`오늘` `어제` `최근 2일` `최근 7일` `이번 주`)과 달력이 있다.
시작일·종료일을 차례로 누르면 범위가 잡히고, **하루 단위**로 `00:00:00 ~ 23:59:59` 가 된다.
미래 날짜는 고를 수 없다.

**조회는 `[조회]` 를 눌러야 나간다.** 모드를 바꾸거나 날짜를 고르는 것만으로는 아무 요청도
안 나간다. 진행 중에는 `[중지]` 로 언제든 끊을 수 있고, 받은 만큼은 화면에 남는다.

### 조회 중에는

```
[실시간|에러|검색] [날짜 ▾]  ● 조회 중 2.6초 · 3,490건 · 요청 5회 · 3.1 MB  [중지]
▓▓▓▓░░░░░░░░░░░░░░░░░░░░░░░░░░░░
```

**진행률(%)은 일부러 안 그린다.** CloudWatch 는 매치가 0건인 페이지에서 스캔 위치를
알려주지 않아, 에러처럼 드문 조건이면 진행률이 멈춘 채 거짓말이 된다. 대신 **언제나
움직이는 값**만 쓴다 — 경과(0.25초마다 브라우저가 셈) · 요청 수 · 수신량 · 건수.

결과가 거의 없을 때도 `조회 중 3.3초 · 0건 · 요청 6회 · 2 KB` 처럼 경과와 요청이 계속
올라가므로 멈춘 것으로 오해하지 않는다.

**실시간에는 막대가 없고 남은 시간이 뜬다.**

```
● 추적 중 58:53 · 30건 · 요청 25회 · 45 KB   [연장]  [중지]
```

기본 60분 뒤 자동으로 멈춘다(5분 남으면 노란색). 더 봐야 하면 **남은 시간 오른쪽의
`[연장]`** 을 누른다 — **설정된 자동 정지 시간만큼** 더해지고, 여러 번 눌러 쌓을 수 있다.

멈춘 뒤 `[시작]` 을 누르면 **쌓아 둔 줄을 버리고 처음부터** 받는다. 업무시간 내내 이어
보려면 멈추기 전에 연장하는 게 맞다. 자동 정지를 `안 함` 으로 두면 연장 버튼은 사라진다.

**끝나도 결과는 안 지운다.** '몇 건을 얼마나 받았나' 는 조회가 끝난 **뒤에** 보고 싶은
값이기 때문이다. 초록이 걷히고 회색으로 남는다:

```
조회 완료 21.6초 · 7,225건 · 요청 12회 · 8.2 MB
추적 중지 · 25건 · 요청 3회 · 30 KB
```

다음 조회를 시작하면 초기화된다.

### 타임라인

```
타임라인 · 30분 단위 · 검색어 일치   에러 41   7,714건   선택 08-13 17:00 ~ 17:30 · 132건  [선택 해제]
▁▁▂▁▃▃▄▆▅▇█▆▄▃▄▅▇▆██▓▓█▆▃▂▂▁
08-13 00:00        08-13 05:59        08-13 11:59        08-13 17:59        08-13 23:59
```

- **에러·예외가 있는 구간은 빨갛다.** 수천 줄을 눈으로 훑지 않아도 어디가 터졌는지 보인다.
- **끌어서 구간을 고르면 목록이 즉시 좁혀진다.** 막대 하나를 클릭하면 그 칸만.
- 이건 **받은 이벤트를 세는 것뿐**이라 CloudWatch 요청이 하나도 안 늘어난다.
  구간을 고르는 것도 재조회가 아니라 화면에 있는 것을 거르는 것이다.
- 끝의 `전체` / `검색어 일치` / `에러·예외만` 은 이 막대가 무엇을 센 것인지 말한다.

| 조작 | |
|---|---|
| **타임라인 드래그** | 그 구간으로 목록 좁히기 (요청 없음) |
| 목록의 **trace_id 클릭** | 상세 열기 |
| 상세에서 **span 줄 클릭** | 그 하위를 접기/펴기 (접으면 `+N`) |
| 긴 값의 **`⋯ 더보기`** | 접힌 값 펼치기 |
| 상세 **왼쪽 모서리를 끌기** | 패널 폭 조절 |
| **목록 클릭** 또는 `Esc` | 상세 닫기 (팝오버가 열려 있으면 그것부터) |

## 읽는 법

| 마커 | 뜻 |
|---|---|
| `●` | **wide** — 요청 하나의 루트 span |
| `↳` | **call** — 그 안의 내부 호출 |
| `⇡` | 부모 span 이 조회 범위 밖 |
| `·` | **narration** — `log.info` 류 |
| (없음) | JSON 이 아닌 평문 줄. **한 글자도 손대지 않는다** |

- **trace_id 컬럼**은 요청마다 색이 다르다. **뒤 12자리**를 보여주는데, 앞 8자리는
  생성 시각이라 같은 시각의 요청끼리 구분이 안 되기 때문이다.
- 들여쓰기는 span 중첩 깊이다.
- **소요시간**은 느릴수록 눈에 띈다 (`MILOG_SLOW_MS` 기본 1000ms).

### 속성은 목록에 안 싣는다

목록은 **훑는 화면**이다. 한 줄에 속성을 세 개씩 잘라 붙여 봐야 시간·이름·소요시간을
읽는 눈만 흐린다. 궁금하면 **trace_id 를 눌러 상세에서 전부** 본다.

```
11:45:00.121 INFO  55ea20212d8d ● BatchDevController.renew                6ms
11:45:00.117 INFO  55ea20212d8d   ↳ SchedulerService.findRenewNotiTarget  1ms
11:45:00.116 INFO  55ea20212d8d     ↳ SELECT orders                       1ms
```

상세에서도 두 가지는 걸러낸다. 단 **사용자 정의 속성은 절대 안 숨긴다** —
숨길 이유를 도구가 알 수 없기 때문이다.

| 숨기는 것 | 왜 |
|---|---|
| `code.function` · `code.namespace` | span 이름을 그대로 다시 적는다 (`OrderService.findOne` 옆에 `code.function=findOne`). **실제로 겹칠 때만** 숨기므로, span 이름을 다르게 붙이면 그대로 남는다 |
| DB span 의 `db.*`(단 `db.statement` 제외) · `server.*` | 매 쿼리마다 같은 접속 정보가 통째로 붙는다 — 호스트·포트·계정·스키마. 쿼리를 읽는 데 도움이 안 되고, `db.connection_string` 과 `server.address` 는 **내부 엔드포인트를 화면에 그대로 띄운다**(스크린샷으로 새어 나간다) |

`server.*` 는 **DB span 에서만** 숨긴다 — HTTP 호출 span 에서는 `server.address` 가
'어느 서비스가 죽었나' 라 가장 중요한 값이다. 쿼리문이 없는 DB span 이면
`db.operation`·`db.sql.table` 은 남긴다 (그마저 지우면 빈 줄이 된다).

## 설정

헤더 오른쪽 [설정] 버튼으로 연다. 화면 가운데 모달로 뜨고, 열려 있는 동안 뒤는 눌리지 않는다 — [닫기] 로만 닫힌다.

| | |
|---|---|
| **테마** | 시스템 / 라이트 / 다크. '시스템' 은 OS 를 따르고, 나머지는 OS 를 무시하고 고정한다 |
| **글자 크기** | 11~15px. 작은 글씨도 함께 커진다 |
| **스택에서 하이라이트할 패키지 리스트** | 콤마로 여러 개. 예외 스택 수십 줄 중 내 코드만 밝게 본다. 비우면 안 함 |
| **목록에서 숨길 span.name** | 헬스체크 쿼리처럼 목록을 덮는 span 을 이름 **완전 일치**로 숨긴다. 항목별 추가·수정·삭제. 목록과 타임라인에서만 빠지고 trace 상세에는 그대로 보인다. 지우면 바로 다시 나타난다 |
| **소요시간 색** | 주의(노랑)·느림(빨강) 기준 ms. 바꾸면 **이미 그려진 줄도 다시 칠한다** |
| **실시간 자동 정지** | 30 / 60 / 120분 / 안 함 |
| **폴링 간격** | 3 / 5 / 10초. **CloudWatch 요청 수에 직결** — 실측상 10초면 3초의 절반 이하 |

**설정은 브라우저가 아니라 상태 디렉터리(`settings.json`)에 저장된다.** `--port` 기본값이
`0`(빈 포트 자동)이라 실행할 때마다 주소가 바뀌는데, 브라우저에 저장하면 그때마다 사라지기
때문이다. 팝오버 아래에 저장 위치가 찍혀 있다.

## 환경 변수

**우선순위: 설정 > 환경 변수 > 내장 기본값.** 환경 변수는 설정을 한 번도 안 바꿨을 때의
기본값이 된다 — 화면에서 바꾸는 순간부터는 저장값이 이긴다.

| 변수 | 뜻 |
|---|---|
| `MILOG_APP_PACKAGES` | 하이라이트할 패키지, 콤마 구분 (예: `com.acme`). **기본은 안 함** |
| `MILOG_SLOW_MS` | 느림(빨강) 기준 ms. 기본 1000 |
| `MILOG_SLOW_WARN_MS` | 주의(노랑) 기준 ms. 기본 200 |
| `MILOG_PROFILE_PREFIX` | 프로필 목록 접두어 |
| `MILOG_STATE_DIR` | 캐시·설정 파일 위치 |
| `MILOG_NO_UPDATE=1` | 자동 업데이트 끄기 |
| `MILOG_DEBUG=1` | 오류 시 스택 출력 |

## AI 에이전트에서 쓰기 (MCP)

`milog mcp` 는 Claude Code 같은 MCP 클라이언트가 로그를 직접 조회하게 해 주는 stdio 서버다.
화면과 같은 로직으로 읽되, 결과는 **AI 가 읽기 좋게 줄여서** 돌려준다 — 같은 예외는 묶어서 횟수만,
스택은 앞부분과 `Caused by`·내 코드 프레임만, trace 는 span 트리 텍스트로. 읽기 전용이다.

```
에러 314건 · 21종류 · 그룹 3개 · 1d ~ 지금
그룹별: /app/qa-batch 300+ · /app/qa-order 10 · /app/qa-web 4
```

### 등록

```bash
milog --version     # 1.1.0 이상이어야 한다. 낮으면 npm i -g @ohg0219/milog@latest
claude mcp add milog -- milog mcp -p my-logs -g qa-
```

`my-logs`·`qa-` 는 예시다. `-p` 는 `~/.aws/config` 의 **프로필 이름**, `-g` 는 **로그 그룹 이름 또는 조각**이다
(`qa-` 하나로 `/app/qa-web`·`/app/qa-api` 가 다 잡힌다). 둘을 주면 **그 범위로 고정**돼서,
AI 가 다른 계정이나 그룹으로 넘어갈 수 없다. 안 주면 호출마다 AI 가 고른다.

> **1.1.0 보다 낮은 milog 로 등록하면 안 된다.** 옛 버전은 `mcp` 를 명령으로 모르고 위치 인자로 넘겨서
> **웹 서버를 띄우고 브라우저를 연다.** stdout 에 서버 안내가 찍히니 Claude Code 에는 원인 없이
> '연결 실패' 만 보인다. 등록 전에 `milog --version` 부터 본다.

팀이 같이 쓰려면 저장소 루트의 `.mcp.json` 에 둔다:

```json
{
  "mcpServers": {
    "milog": { "command": "milog", "args": ["mcp", "-p", "my-logs", "-g", "qa-"] }
  }
}
```

**Windows** — `milog` 를 못 찾으면 `cmd /c` 로 감싼다:

```bash
claude mcp add milog -- cmd /c milog mcp -p my-logs -g qa-
```

**PowerShell 에서는 `--` 가 사라진다.** `claude` 가 npm 이 만든 `claude.ps1` 로 실행되는데,
PowerShell 이 스크립트에 인자를 넘기면서 `--` 를 자기 문법으로 먹어 버린다. 그러면 뒤의 `-p`·`-g` 가
claude 의 옵션으로 읽혀 `error: unknown option '-g'` 가 난다. 둘 중 하나로 피한다:

```powershell
claude.cmd mcp add milog -- milog mcp -p my-logs -g qa-     # .ps1 대신 .cmd 를 직접
claude mcp add milog '--' milog mcp -p my-logs -g qa-       # -- 를 따옴표로 감싸기
```

### tool

| tool | 하는 일 |
|---|---|
| `list_sources` | 프로필·로그 그룹 목록 (고정했으면 그 범위만) |
| `find_errors` | 구간 안의 에러를 종류별로 묶어 많은 순으로. 횟수·시각·스택 앞부분·예시 trace_id |
| `search_logs` | 검색어가 든 줄을 레벨 무관하게 시간순으로. 대소문자 구분, 콤마 = 모두 포함 |
| `get_trace` | trace 하나를 span 트리 텍스트로. 시작 기준 오프셋·느린 span·예외 |

그다음은 말로 시키면 된다 — "최근 1시간 에러 요약해줘", "주문 12345 로그 찾아줘", "이 trace 왜 느렸어?".
보통 `find_errors` 로 무엇이 터졌는지 보고, 거기 나온 trace_id 로 `get_trace` 를 불러 원인을 좁힌다.

검색과 에러를 한 tool 로 합치지 않은 이유는 화면과 같다 — [검색과 에러를 왜 섞지 않나](#검색과-에러를-왜-섞지-않나).

### 어떻게 읽나

**어디까지 봤는지 반드시 밝힌다.** 조용히 자르면 AI 는 받은 것을 전부로 믿는다.

- **상한은 그룹마다** 건다(`find_errors` 기본 300건, `search_logs` 100건). 전체에 하나만 걸면 시끄러운 그룹이
  상한을 다 써서 다른 그룹의 드문 에러가 통째로 사라진다(실측: 배치 하나의 예외 500건에 다른 서비스의 NPE 가 가려짐).
  상한에 걸린 그룹은 `300+` 로 표시된다.
- **호출 하나는 90초까지만** 돈다. 넘으면 받은 데까지 요약하고 다 못 훑은 그룹을 이름으로 밝힌다.
  기본 구간은 1시간이고, 길수록 느리다 — 실측으로 12그룹·1일 약 55초.
- 날짜를 콕 집지 않으면(`since` 가 `7d` 같은 상대값이고 `until` 이 없으면) **최근 쪽부터** 1시간·6시간·1일… 으로
  거슬러 올라가며 훑는다. CloudWatch 는 오래된 쪽부터 읽기 때문에, 7일을 한 번에 주면 시간이 오래된 쪽에서
  다 떨어져 **오늘 로그에 닿지도 못한다**(실측: 7일 0건, 같은 검색 1일 1건). 시간이 모자라면
  `10-14 10:53 이후만 다 훑었습니다` 처럼 어디까지 봤는지 알려 준다.
- `get_trace` 에 **32자리 trace_id 를 주면 구간이 필요 없다.** 앞 8자리가 생성 시각(epoch 초)이라
  그 앞뒤만 찾는다 — 3일 전 trace 도 3초 안에 열린다. 그 구간에 없으면 최근 1시간에서 한 번 더 찾는다.
- 검색어는 로그에 찍힌 모양 그대로 준다 — `"orderId":12345`(JSON 속성), `orderId=12345`(메시지).
  원본 줄은 JSON 이라 trace_id 까지 들어 있어서, `orderId,12345` 처럼 값만 따로 주면 trace_id 에 `12345` 가 든 줄까지 걸린다.
- span 줄에는 이름을 되풀이한 메시지(`GET /checkout, 841 ms`) 대신 `business_attributes` 전부와
  응답 코드·`url.query`·`db.statement` 를 싣는다. 같은 `GET /checkout` 이라도 플로우 단계와 응답 코드로 구분된다.
- 자격증명이 만료되면 tool 이 `aws sso login ...` 안내를 돌려준다. Claude Code 라면 `! aws sso login --sso-session ...` 으로 바로 실행한다.
- **자동 업데이트를 하지 않고 알리기만 한다** — stdout 이 통신 통로라 설치·재실행이 끼어들면 연결이 깨진다.
  새 버전이 있으면 세션의 첫 응답 끝에 한 번 `npm i -g @ohg0219/milog@latest` 안내가 붙는다(AI 가 전해 준다).
  올린 뒤 MCP 서버를 다시 연결하면 된다. `MILOG_NO_UPDATE=1` 이면 확인도 안 한다.

### 다른 CloudWatch MCP 와 무엇이 다른가

AWS 의 CloudWatch MCP 서버(`awslabs.cloudwatch-mcp-server`)와 **같은 QA 로그 그룹 12개에 같은 질문**을 해 봤다
(2026-10, 그쪽은 AI 가 쓸 법한 Logs Insights 쿼리를 직접 작성).

| 질문 | cloudwatch-mcp-server | milog mcp |
|---|---|---|
| 1일 에러 요약 — 포맷을 모르는 쿼리 | 13초 · **205 KB** · 상위가 INFO 줄('error' 단어만 있어도 걸림) | 55초 · 11.6 KB |
| 1일 에러 요약 — 포맷을 아는 집계 쿼리 | **11초** · 21 KB · 결과는 milog 와 같음 | (위와 같음) |
| 3일 전 trace 열기 | 16초 · 4.5 GB 스캔 · 시간순 평면 목록(UTC) | **3초** · span 트리 · 예외·스택 |
| 도구 스키마 (대화마다 차지) | 19개 · 90,703자 | 4개 · 3,534자 |
| 조회 API · 비용 | Logs Insights · 스캔 GB 과금(질문당 약 1.6 GB) | FilterLogEvents · 스캔 과금 없음 |

- **넓은 구간 집계는 그쪽이 빠르고 강하다.** Logs Insights 가 서버에서 병렬로 훑는다. 시간대별·엔드포인트별
  통계 같은 질문, 메트릭·알람은 그쪽 몫이다.
- **milog 는 AI 가 이 로그 포맷과 쿼리 언어를 몰라도 된다.** 그쪽도 쿼리만 잘 쓰면 에러 요약 품질은 같지만,
  그러려면 AI 가 `span_exception`·`context_map` 같은 구조를 알아야 한다. trace 를 트리로 읽는 건 milog 만 한다.
- 그래서 **대체가 아니라 같이 붙이는 것**이 맞다 — 인프라·집계는 CloudWatch MCP, 이 포맷의 앱 로그 해석은 milog.

범용 AWS MCP 서버(API 를 직접 부르는 쪽)로 `"ERROR"` 텍스트 검색을 했을 때는 결과의 20% 가 WARN 이었고,
한 그룹이 경고 없이 1,000건에서 잘렸다.

## 자동 업데이트

실행할 때마다 최신 버전을 확인하고, 새 게 있으면 **시작하기 전에** 설치한다.

```
$ milog
  새 버전 1.1.0 설치 중…
  ✓ 1.1.0 으로 업데이트했습니다.

  milog  →  http://127.0.0.1:52413/?t=…      ← 여기서부터 새 버전
```

설치한 뒤 **새 코드로 자기 자신을 다시 띄운다.** 그냥 두면 이미 메모리에 로드된 옛 파일로
계속 돌아서, 업데이트했다고 해 놓고 옛 버전이 뜬다.

끝난 뒤가 아니라 시작 전인 이유: 이 도구의 주 명령은 **웹 서버라 Ctrl+C 로만 끝난다.**
종료 시점에 걸어 두면 신호 처리 경로에서 잘려 영영 돌지 않는다.

**이때 npm 레지스트리에 통신한다.** 그 외에는 AWS 하고만 통신한다. 끄려면 `MILOG_NO_UPDATE=1`.
아래 경우에는 **확인조차 하지 않는다** — CI(`CI` 환경변수), 터미널이 아닐 때,
npm 전역 설치본이 아닐 때(소스에서 직접 실행 중일 때).
`milog mcp` 는 예외로 **확인은 하되 설치하지 않고 알리기만** 한다 ([MCP](#ai-에이전트에서-쓰기-mcp) 참고).

게시자가 바뀌면 설치하지 않고 경고만 한다 — 공동 관리자가 추가되거나 소유권이 넘어간 경우를 막는다.

## 안전장치

이 서버는 **당신의 AWS 자격증명으로 로그를 읽어 준다.** 그래서 아무나 못 붙게 막아 뒀다.

- **`127.0.0.1` 에만 바인딩** — 같은 네트워크의 다른 기기에서 접근 불가
- **기동할 때마다 새 토큰** — 주소에 실려 있고, 없으면 403
- **`Host` 헤더 검증** — DNS rebinding 방어
- **CORS 를 열지 않는다** — 페이지는 외부 요청이 전혀 없다 (CSP 로도 막음).
  탭 아이콘조차 인라인 SVG 라 파일을 가지러 나가지 않는다

**탭을 닫으면 폴링도 멈춘다.** 다만 **다른 탭으로 옮기는 것만으로는 안 멈춘다** —
실시간을 켜 두고 그 서비스를 보러 가는 게 가장 흔한 사용법인데, 정작 재현하는 동안
로그가 안 쌓이면 '실시간' 이 아니기 때문이다. '켜둔 채 잊기' 는 **60분 자동 정지**가 막는다.
접속이 없는 채로 `--idle-minutes` 가 지나면 서버도 스스로 종료한다.

`milog mcp` 는 포트를 열지 않는다 — 등록한 MCP 클라이언트의 자식 프로세스로 돌고 stdin/stdout 으로만 말한다.

- **읽기 전용** — 로그를 읽는 API 만 부른다
- **`-p`·`-g` 로 범위 고정** — AI 가 그 밖의 계정·로그 그룹을 요청하면 거부한다
- **AI 에게 주는 것도 화면과 같은 규칙으로 거른다** — DB span 의 접속 문자열·내부 엔드포인트(`db.connection_string`,
  `server.address`)는 싣지 않는다. 단 `business_attributes` 는 전부 싣는다(개발자가 일부러 남긴 값이다).
  거기에 IP·요청 본문이 있으면 그대로 AI 에게 간다 — 운영 로그에 붙일 때는 이 점을 감안한다

## 비용

조회에 쓰는 `FilterLogEvents` 는 **요청당 과금이 없고**, 서버측에서 거른 뒤 매치만 전송된다.
스캔량이 아니라 **전송량(GB)** 이 비용이다 — 화면 하단에 요청 수·이벤트 수·수신량이 계속 뜬다.
`milog mcp` 도 같은 API 를 쓰고, 응답 끝에 `(CloudWatch 요청 13회 · 5.9 KB)` 처럼 사용량을 적는다.

Logs Insights 는 쓰지 않는다. Logs Insights 는 **스캔한 GB 만큼** 과금된다 — 실측으로 QA 그룹 12개 하루치
에러를 한 번 물으면 약 1.6 GB 를 스캔했다. 넓은 구간을 훨씬 빨리 훑는 대신 질문마다 돈이 든다.

## 개발

```bash
npm install
npm test
node bin/milog.js --help
```

의존성은 AWS SDK 세 개와 MCP 서버용 두 개(`@modelcontextprotocol/sdk`, `zod`)뿐이고 개발 의존성은 없다
(테스트는 Node 내장 `node --test`).

MCP 를 고치면서 Claude Code 로 바로 써 보려면 전역 설치본 대신 저장소 코드를 등록한다.
코드를 고친 뒤 `/mcp` 에서 다시 연결하면 반영된다:

```bash
claude mcp add milog-dev -- node <저장소 경로>/bin/milog.js mcp -p my-logs -g qa-
```
